# Architecture

## 1. Overview
boba-cafe is a Roblox multiplayer cafe roleplay game: customers order drinks and food, baristas (players who are clocked in) claim orders, prepare them in the kitchen, and clean spills, and everyone collects cosmetics (pets, nametags, particles) from capsules and the shop. It uses Rojo for file sync, Wally for packages, Knit for server/client structure, React for UI, and ProfileStore for player data.

## 2. Single-Place Model
The game is one Roblox place. The authored world (kitchen, ordering counters, spill areas, models, sounds) is saved in the place file; this repository holds only the scripts and the Rojo tree that syncs into it.

| Piece | Where | Notes |
| --- | --- | --- |
| Scripts | This repository, mapped by `default.project.json` | Server, client, and shared Luau. |
| Authored world and assets | The Roblox place file (not in the repository) | `workspace.Assets` (Kitchen, Kitchen `TrashCans`, Spills, NPC, AreaLimits), `workspace["Ordering System"]`, `workspace.Customers` (runtime NPC folder), `ReplicatedStorage.SelectorModels`, `ReplicatedStorage.SharedStorage` (`CleanlinessStorage`, `NPCStorage`, `KitchenStorage`, tools, animations, effects), `ReplicatedStorage.AreaLimits.BreakGates`, the `InventoryEvent` remote in `ReplicatedStorage.Networking`, `SoundService.SFX` / `Music`. |
| Packages | `Packages/`, `ServerPackages/` (generated by Wally, gitignored) | |

Authored content may be missing or renamed (the place is edited separately from this repository), so scripts resolve it defensively: at `KnitStart` or at use time, never at require time, through `src/shared/Utility/WorldPath.luau` (`find` returns nil without yielding; `waitFor` waits for a path against one shared deadline) or a bounded `WaitForChild`. A missing folder logs a `warn` naming the path and disables only the feature that needs it (kitchen, spills, ordering screens, pick-up beam); it must not stop Knit, the HUD, or other systems. Do not hide a wrong path by inventing content in code. Document each dependency on authored content, with its exact instance path, in the owning system in `SYSTEMS.md`. Remotes for `RedeemCode` and `GetPurchases` are the exception: their scripts create the `Networking` folder and the RemoteFunction when absent.

## 3. Source Layout
* **`src/shared/`** — Code used by both sides, mapped to `ReplicatedStorage.Shared`:
  * `Configuration/` — Tunable data: profile template, kitchen, spills, capsules, gamepasses, teams, item definitions (`InventoryItemDefinitions/`), customers (`CustomerConfig`, `CustomerDialogue`), shifts (`ShiftConfig`), progression (`Progression`), cafe rating (`RatingConfig`), real orders (`RealOrderConfig`).
  * `Inventory/` — Inventory model (`InventoryServer`, `InventoryClient`, `InventoryItem`, `ItemActions`, `CapsuleUtil`). `init.luau` returns the server or client implementation by `RunService:IsServer()`.
  * `Kitchen/` — Recipe data, recipe constructors, kitchen types.
  * `Ordering/` — Menu definitions (`Menu`, including the launch allowlist) and `OrderSpec` (grading a tool against an order).
  * `Pets/` — Pet display helpers shared by server and client.
  * `UI/` — React app, `Styles.luau`, `Components/`, `Pages/`, `Hooks/`, `Utility/`, `Stories/`.
  * `Utility/` — `RankUtil`, `GamepassUtil`, `WorldPath`, `Animator`, `ItemFader`.
* **`src/server/`** — `ServerScriptService.Server`:
  * `init.server.luau` — Starts Knit, dispatches `PlayerAdded` / `PlayerRemoving` to services.
  * `Modules/` — Knit services (each file or folder with `init.luau`), including `CustomerService` (with `Npc` and `Rules`), `UniformService`, `TrashService`, `ShiftService`, `ProgressionService`, `RealOrderService`, `CafeRatingService`, and `AnalyticsEvents`.
  * `Scripts/` — Standalone server scripts (`ProcessReceipt`, `PromoCodes`, `Teams`).
  * `Configuration/` — Server-only data (`PromoCodes`).
  * `Tests/` — TestEZ specs and the Studio-only runner.
* **`src/client/`** — `StarterPlayerScripts.Client`:
  * `init.client.luau` — Starts Knit, dispatches `PlayerAdded` / `PlayerRemoving` to controllers.
  * `Modules/` — Knit controllers (`App/AppEntry`, `DataController`, `OrderController`, `KitchenController`, `PetController`, `SpillController`, `AreaController`, `AppDialogs`, `Pets/`) and `KitchenGuidance` (pure logic, not a controller).
  * `Scripts/` — Standalone client scripts (`PlayerOverheads`).
* **`docs/`** — Durable documentation. **`.review/agent-workflow/`** — Agent board, decisions, and task evidence.

## 4. Rojo Project Composition
`default.project.json` composes the DataModel:

* `src/shared` → `ReplicatedStorage.Shared`
* `Packages` → `ReplicatedStorage.Packages`, with `ServerPackages` nested as `ReplicatedStorage.Packages.Server` (server code requires `Packages.Server.ProfileStore`; the nesting is how the server-only package is reached).
* `src/server` → `ServerScriptService.Server`
* `src/client` → `StarterPlayer.StarterPlayerScripts.Client`
* A baseplate, lighting, and sound properties are declared in the project; the authored place supplies everything else.

`.gitignore` excludes `/default.project.json`, `/sourcemap.json`, `/Packages`, `/ServerPackages`, and `/.vscode`; a fresh clone must recreate the project file before `rojo serve` works. Treat any change to the tree mapping as a Jack-visible change and note it in the task result.

## 5. Server/Client Boundary
Knit is the transport for services and controllers.

* **Server:** Authoritative for player data, currency, inventory, orders, shift (clock-in) state, kitchen actions, spills, purchases, and badges. Group rank is informational and does not gate gameplay.
* **Client:** Owns input, camera, presentation, and UI rendering. It asks the server to act and renders replicated state.
* **Knit services:** A service's `Client` table is its public API (methods and `Knit.CreateSignal()` signals). Clients reach it with `Knit.GetService("Name")`.
* **Raw remotes:** Some features use RemoteEvents/RemoteFunctions in `ReplicatedStorage.Networking` (`InventoryEvent`, `RedeemCode`, `GetPurchases`). `InventoryEvent` is authored in the place; `RedeemCode` and `GetPurchases` are created in code by `Scripts/PromoCodes.server.luau` and `Scripts/ProcessReceipt.server.luau` (find or create the folder and the RemoteFunction). Their server handlers live in `Scripts/` and `Inventory/`. `ClaimRank` no longer exists.
* **Replication:** `ReplicaService` (server) and `ReplicaController` (client) replicate the player profile and the global cleanliness value. `ByteNet` is available for packet-based networking.
* **Startup:** Both `init` scripts call `Knit.AddServicesDeep` / `AddControllersDeep` on `Modules`, then `Knit.Start()`. On start, the server calls each service's `PlayerAdded` for current and future players; on removal it runs every `PlayerRemoving` first and `DataService` last. The client does the equivalent for controllers after `ReplicaController.RequestData()`.

## 6. Data Flow

* **Player data:** `DataService` loads a profile with ProfileStore (`PROFILE_STORE_NAME`, template from `Configuration/ProfileTemplate.luau`), wraps it in a Replica owned by that player, and runs the `PlayerSetup` functions (nickname prompt, cosmetics, pets, group reward). Other services call `DataService:GetDataAsync(player)` and write through `:SetValue(path, value)`.
* **Client data:** `DataController` receives the Replica through `ReplicaController` and exposes it with `GetDataAsync()`. UI reads from it and never mutates server state.
* **Inventory:** Items live under `Inventory.Items.<Type>` in the profile. The inventory module builds typed item objects over that data; the server inserts, equips, stacks, and removes, and the client mirrors changes through `InventoryEvent`.
* **Shift:** `ShiftService` owns a `ClockedIn` attribute on each player (server-set, default clocked in). `KitchenService`, `OrderService`, and `Spill` consult `ShiftService:IsClockedIn` on the server; `Teams.server.luau` and the HUD read the attribute.
* **Orders:** The Ordering and MobileOrder pages send `OrderService.Client:CreateOrder(userId, { { Category, Item, CustomInfo }, ... })` for the calling player only; the server rebuilds each item from `Shared.Ordering.Menu` and rejects unknown or invalid choices. Staff screens and pick-up prompts drive claiming (clocked-in players) and collection. The service owns the order list, barista queue, status transitions, and the pick-up models, and pushes updates through its `Client` signals.
* **Purchases:** `MarketplaceService.ProcessReceipt` and gamepass checks run on the server; UI only prompts purchases and reflects results. Receipts are durable: the `PurchaseId` is recorded in the profile (`ProcessedReceipts`) and saved with `DataService:SaveAsync` before `PurchaseGranted`; anything unmapped, unapplied, or unconfirmed answers `NotProcessedYet`.
* **Customers:** `CustomerService` spawns NPCs from the authored `workspace.Assets.NPC` contract into `workspace.Customers` and assigns each waiting customer to a clocked-in barista. Assignment is pushed to that barista through `CustomerService.Client.TicketChanged`. The Serve prompt on the NPC runs the checks listed in `SYSTEMS.md` before any tool is taken.
* **Dialogs:** Server code asks a player a question through `DialogService`; `AppDialogs` (client) renders a component from `Shared.UI.Components.Dialogs` and returns the answer.
* **UI:** React components read from controllers and data bindings and dispatch Knit calls.

## 7. Package Dependencies
Packages defined in [`wally.toml`](../wally.toml):

* **`knit`** — Service/controller framework and signals.
* **`promise`** — Asynchronous flow control.
* **`janitor`, `goodsignal`** — Cleanup and in-process signals.
* **`profilestore`** (server only) — Player data persistence.
* **`replicaservice` / `replicacontroller`** — Profile and global-state replication.
* **`react` + `react-roblox`** — React 17 UI.
* **`react-spring`** — UI animation.
* **`loader`, `table-util`** — General utilities (two different `TableUtil` entries currently share one key in `wally.toml`; resolve before adding or updating packages).
* **`simplepath`** — Pathfinding.
* **`bytenet`** — Packet networking.
* **`zone`** — Zone detection.
* **`cmdr`** — Admin commands.
* **`testez`** — Testing framework.
