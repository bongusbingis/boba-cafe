## Verdict: **BLOCK** (until the P0 and P1s are fixed or Jack accepts them)

The receipt path is sound. ProfileStore is used correctly, and I found no route that grants twice, grants
without recording, or answers PurchaseGranted before a confirmed save, apart from the deliberate record-failure
branch. The blockers are elsewhere:
1. In the captured Play session, client Knit never starts (P0, existing code, not caused by this diff).
2. Both ordering UIs report every order as failed.
3. `CreateOrder`, now open to all players, puts unvalidated client strings on world screens and can break the
   order boards.
4. Spills turn themselves off on a correctly built place.
5. Tripping on a spill can freeze the player for good when the fall animation is missing.

## Focus-area notes (no finding)

- **Purchases.**
  - The callback is assigned before any yield, and it answers NotProcessedYet until Knit has started.
  - An unmapped product answers NotProcessedYet. A player who is gone, data that is missing or times out, or an inactive profile all answer NotProcessedYet.
  - Grant and record happen back to back with no yield in between. `SaveAsync` checks the copied `LastSavedData` for the `PurchaseId`.
  - `LastSavedData` is a fresh copy, not an alias of `Profile.Data`. On load it is a `DeepCopyTable`, and on save it is the deserialized `UpdateAsync` result. The mock path also copies.
  - The listener is connected before `Save()`. A session-end save also fires `OnAfterSave`, so leaving mid-save still confirms.
  - If the save is not confirmed, the in-memory record makes Roblox's retry take the "already granted" path. A server crash before any save loses both the grant and the record, so the retry correctly grants once.
  - `inFlight` blocks re-entry. Pruning at 200 removes only old, already acknowledged ids.
- **Remote trust.**
  - `CreateOrder` checks `customerId == player.UserId`, validates types and item count, keeps one open order per player with a 5 s debounce, and copies only the array part. See #3 for the item content.
  - `ShiftService.Client:SetClockedIn` checks for a boolean and has a per-UserId 2 s debounce that is cleared in `PlayerRemoving`.
  - The kitchen prompts, claiming and the queue all check clock-in on the server. Deposit stays open to the preparer by design. Cleaning checks clock-in.
- **Continued play.** The join kick is removed (DEC-004). Nothing new kicks or blocks a player. The world lookups in OrderService, KitchenService, OrderController, KitchenController and TopBar are bounded and happen in KnitStart or in an effect. InteractionRunner now pcalls its sequence, so the debounce cannot stick.
- **Removed functionality.**
  - `ClaimRank`, `RankingService`, `GlobalMulti` and `PlayerSelectPage` have no remaining callers in `src`.
  - `CanUseOrderingSystem` is still used only by `BadgeService:246`, and `RankUtil` still defines it.
  - The duplicate `TableUtil` key is gone. The remaining fork has `Shuffle` and `Random`.
  - Order lifecycle: queue, claim, deposit and pickup logic is unchanged apart from the gates. Clocking out leaves the queue and keeps an order already in preparation. Customers or baristas who leave are handled in `_updateOrders`.
- **Tests.**
  - The CurrencyService and ShiftService specs test behaviour through the public API with fakes.
  - All three specs are discovered by `RunTests.server.luau` (`TestEZ.run(script.Parent)`). Gauge's capture shows 122/122 passing.
  - The specs don't cover the order-content validation (#3), the receipt path (#10) or any client UI (#2, which tests would have caught).
